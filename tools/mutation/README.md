# mutation — テストが機構を守っているかを測る

各機構を 1 つずつ壊し、落ちるテストの数を数える。**0 件しか落ちない機構は、誰も
検証していない** — 通っているのはテストが弱いからで、実装が正しいからではない。

```
tools/mutation/mutate.sh result.txt
```

## 読み方

| 落ちた数 | 意味 |
|---|---|
| 0 | その機構を検証しているテストが無い。テストを足す |
| 1–2 | 一つの形でしか確かめていない。別の形も足す |
| 多い | 複数の観点から守られている |
| `COMPILE_NG` | 注入した位置が悪くコンパイルが通らなかった。測れていない |

`COMPILE_NG` を「0 件」と読み違えると、**測れていないものを「検証されていない」と
誤診する**。初版のスクリプトは引数リストの途中に注入していて、全機構が 0 件に見えていた。

## 2026-08-01 の測定

| 機構 | 落ちたテスト |
|---|---|
| union の丸ごと読み | 66 |
| 型の単一化 | 40 |
| 条件型の評価 | 37 |
| union の整理 | 14 |
| callable の束縛 | 12 |
| テキストの単一化 | 8 |
| エイリアス展開 | 3 |
| 精密化の置換 | 5 (当初 2。分岐ごとに補強した) |

## 変異の選び方

**何を測りたいかで変異を選ぶ。** 機構を丸ごと殺す変異は「その機構を検証しているテストの数」を
測る。一方、解決した型に `mixed` を足す変異では、268 件中 4 件しか落ちない — これは弱さでは
なく設計どおりで、表示側の整理 (`TypeUnionSimplifier`) が余計な型を吸収するため。

変異が落とすテストが少ないとき、それが「テストが弱い」のか「その変異では壊れない設計」なのかを
先に決める。決めずに件数だけ見ると、健全な設計を欠陥と誤診する。

## この測定が実際に見つけたもの

型を検証する assert に「解けたのに粗い型が混ざっていないか」を足したところ、array shape を
含む型が `\Probe\array{...}` と修飾されているのが露見した。存在しないクラス名で、部分一致の
assert では通り抜けていた。
